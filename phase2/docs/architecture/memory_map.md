# Memory map

File class: **[1] hand-written architecture document**.

This document defines the architecture-level memory-map policy for T-RECAP Phase 2. It covers CSR address ownership, DDR ring address ownership, HPS runtime configuration, Platform Designer address documentation, and the rules that prevent Linux virtual addresses, HPS physical addresses, and FPGA-visible bus addresses from being confused.

## Address-space rule

There are three different address spaces. Mixing them is a real bug.

| Address space | Used by | Example field | Meaning |
| --- | --- | --- | --- |
| HPS physical address | Linux/HPS mapping code | `ring_base_hps_phys` | Physical DDR address as seen by HPS/Linux. |
| HPS userspace virtual address | HPS process after `mmap()` | local pointer only | Process-local pointer. Never written to FPGA CSR. |
| FPGA-visible bus address | FPGA DDR writer master | `ring_base_fpga`, CSR `RING_BASE_*` | Address used by `trecap_ddr_ring_writer.sv`. |

`RING_BASE` is the address as seen by the FPGA DDR writer bus master. It is not a Linux userspace virtual address.

```text

```

The CSR map defines offsets inside the FPGA CSR window. It does not define where the CSR window appears in the HPS physical address map. That board-specific base address belongs in the HPS runtime config and Platform Designer address-map documentation.

## Baseline system path

The memory-visible path is:

```text
FPGA telemetry packetizers
    -> formatted record stream
        -> rtl/hps_bridge/trecap_ddr_record_builder.sv
            -> rtl/hps_bridge/trecap_ddr_ring_writer.sv
                -> FPGA-visible HPS DDR ring address
                    -> HPS DDR ring reader mmap()/cache policy
                        -> UDP streamer
                            -> PC dashboard
```

Reverse command path:

```text
PC command UDP
    -> HPS command parser
        -> HPS command bridge / RFC1982 cache
            -> HPS writes/reads HPS-visible CSR base + generated offset
                -> Avalon-MM CSR adapter (full aperture decode)
                    -> CSR bank
                        -> shadow/commit, replay, or status/control update
```

HPS software shall not process signal samples to compute FFT, IFFT, mask decisions, WOLA, or reconstruction error.

## CSR window

The CSR bank is a 32-bit little-endian, 32-bit aligned memory-mapped register window accessed by HPS through the HPS-to-FPGA lightweight bridge or equivalent.

Architecture-level placeholders:

```text
Cyclone V lightweight aperture:  0xff200000..0xff3fffff inclusive (2 MiB)
CSR base from HPS view:         defined in sw/hps/config/trecap_hps_config.json
CSR span:                       at least 0x100 bytes for Revision G baseline; recommended 4096 bytes
CSR offset source of truth:     spec/generated/csr_map.json
CSR generated C header:         sw/hps/include/generated/trecap_csr.h
CSR generated SV package:       rtl/include/generated/trecap_csr_pkg.sv
```

HPS code shall compute register addresses as:

```text
csr_word_address = csr_base_mapped_pointer + generated_offset
```

Do not duplicate offsets in `sw/hps/src/csr_map.c`, `trecap_csr_bank.sv`, or the PC command client.

The Step 4 DE1-SoC plan assigns the 4 KiB CSR bank at offset zero of the 2 MiB
Cyclone V lightweight HPS-to-FPGA aperture. The interconnect/wrapper must fully
decode the subwindow and leave the rest unmapped. Mirroring the CSR bank because
upper aperture address bits were ignored is a contract violation.

The exported lightweight master carries a 21-bit byte address for the complete
2 MiB aperture. The current CSR leaf consumes only the lower 12 byte-offset bits
for its 4 KiB register window. Those widths describe different layers: the
interconnect or wrapper must first accept only `0x000000..0x000fff` using all
21 master bits, then pass the lower 12 bits to the leaf. It must never truncate
the master address first, because that would alias the CSR bank 512 times.

Step 5 chooses the typed repository wrapper as the fail-closed decode owner in
source RTL. `trecap_avmm_csr_adapter.sv` consumes all 21 byte-address bits and
forwards only the lower 12 bits after the exact 4 KiB range match. It additionally
requires four-byte alignment, full `4'b1111` byteenable for reads and writes, and
single-beat `burstcount=1`. The separate machine contract is
`platform/de1soc/address_map/avalon_csr_adapter.json`.

Step 6 supplies the missing protocol boundary: the raw HPS lightweight AXI master
connects to `trecap_csr_bridge.s0` at offset zero, Qsys inserts AXI-to-Avalon
adaptation, and `trecap_csr_bridge.m0` is exported to the hand-written wrapper.
The wrapper carries the full 21-bit byte address to the adapter; it does not weaken
the decode or introduce aliases. Generated HDL/SOPCINFO and Quartus evidence remain
pending.

If any value above differs from generated headers, the generated schema and this document shall be reconciled before implementation continues.

Step 14 assigns `STATUS.actual_source_mode` to bits 11:10,
`STATUS.transport_epoch_idle` to bit 12, and
`STATUS.source_transition_busy` to bit 13. Existing source-commit pending bit 9
is asserted for an outstanding commit or whenever requested and actual source
mode differ.

`REPLAY_STATUS` uses bit 0 `pending`, bit 1 `last_accept`, bit 2
`last_reject`, bit 3 `start_ready`, bit 4 `replay_active`, bit 5
`replay_path_busy`, bit 6 `replay_path_done`, bit 7 `e2e_busy`, bit 8
`e2e_done`, bit 9 `error`, bit 10 `rearm_required`, and bits 31:16
`result_epoch`; bits 15:11 read zero. The retained accept/reject result is for a
CSR-originated request. Local board-key activity cannot overwrite it.

## Multiword CSR transfer policy

Multiword values shall not be read or written as independent halves.

| Value | Direction | Mechanism |
| --- | --- | --- |
| `THR2[55:0]` | HPS -> FPGA core | `THR2_LO`, `THR2_HI`, `THR2_COMMIT`, frame-boundary apply. |
| `RING_BASE[63:0]` | HPS -> writer | Low/high plus `RING_CONFIG_COMMIT` while telemetry disabled. |
| `RING_RD[63:0]` | HPS -> writer | Low/high shadow plus `RING_RD_COMMIT`. |
| `RING_WR[63:0]` | writer -> HPS | `RING_WR_SNAPSHOT`, then read low/high snapshot. |
| sample/frame counters | core -> HPS | `CORE_COUNT_SNAPSHOT`, then read low/high snapshots. |

No live low/high tearing is allowed.

## DDR ring region

The DDR telemetry ring is a contiguous HPS-visible memory region written by FPGA and consumed by HPS.

Architecture variables:

```text
B = FPGA-visible ring base address
R = ring size in bytes
W = FPGA-owned absolute producer pointer
Rd = HPS-owned absolute consumer pointer
```

Required baseline rules:

```text
R is a power of two.
R is a multiple of 64 bytes.
R is at least 2^20 bytes.
Recommended first implementation R = 32 MiB.
B is 64-byte aligned.
If the bridge requires natural power-of-two region alignment, B is also aligned to R.
Pointers are 64-bit monotonic byte pointers.
off(p) = p & (R - 1)
valid occupancy requires 0 <= W - Rd <= R
```

The DDR ring shall be reserved or allocated so Linux does not use it for unrelated memory.

## DDR ring record policy

Normal records:

```text
header_bytes = 32
payload_bytes = packet-specific
record_length = align64(header_bytes + payload_bytes)
record starts at a 64-byte aligned offset
record shall not cross the physical end of the ring
```

If a normal record would cross the physical end, writer emits a WRAP record that consumes the entire remaining tail. WRAP records are not forwarded to PC and do not consume normal telemetry sequence numbers.

The producer pointer is the commit boundary. HPS shall not read beyond a snapshotted committed producer pointer.

## Ring initialization sequence

HPS software shall perform the sequence below for first bring-up and reconfiguration:

```text
1. Clear CONTROL.telemetry_enable.
2. Clear CONTROL.ring_writer_enable.
3. Pulse CONTROL.telemetry_soft_reset.
4. Write RING_BASE_LO and RING_BASE_HI using FPGA-visible ring base address.
5. Write RING_SIZE_BYTES.
6. Pulse RING_CONFIG_COMMIT while telemetry is disabled.
7. Write RING_RD_LO_SHADOW = 0.
8. Write RING_RD_HI_SHADOW = 0.
9. Pulse RING_RD_COMMIT.
10. Snapshot and verify producer pointer W = 0.
11. Set CONTROL.ring_writer_enable.
12. Set CONTROL.telemetry_enable.
```

Do not enable the writer before ring configuration and consumer pointer commit.

## Memory coherency policy

The Step-13 HPS userspace reader maps the ring read-only from synchronous
`/dev/mem`. Cached mapping is forbidden and
`allow_cached_ring_mapping` shall remain `false` because this reader has no
cache-invalidation mechanism. Before normal mapping, runtime admission must
prove the exact active-DT `no-map` reservation, absence of `reusable`, and no
`System RAM` overlap in an unmasked `/proc/iomem`. A future kernel/DMA driver may
define a different coherency contract, but it must not silently weaken this
baseline.

## Platform address-map document requirements

`platform/de1soc/address_map/address_map.md` shall document:

```text
- HPS-visible CSR base physical address;
- CSR span;
- HPS-to-FPGA lightweight bridge path used for CSR access;
- FPGA-visible ring base address convention;
- HPS physical DDR ring address convention;
- Linux userspace mapping policy;
- ring size and alignment;
- bridge data width and byte-lane behavior;
- maximum burst length if relevant;
- waitrequest behavior if Avalon-MM is used;
- Platform Designer/Qsys system name;
- .sopcinfo location if consumed by scripts or HPS code;
- exact translation from HPS physical address to FPGA-visible ring address.
```

Do not leave address translation as oral knowledge.

For the Step 4 DE1-SoC source freeze, the translation is explicitly an identity
mapping:

```text
ring_base_fpga = ring_base_hps_phys + 0
```

That identity depends on the reviewed Cyclone V boot/remap assumption recorded
in `hps_bridge_regions.json`. A different boot mapping invalidates the source
freeze; software must not guess an alias.

The non-mutating source gate is:

```bash
python3 scripts/check_address_map.py
```

After real Platform Designer generation, the hardware-evidence gate is:

```bash
python3 scripts/check_address_map.py --require-sopcinfo
```

## Address map source hierarchy

When resolving conflicts:

```text
1. Active integrated spec under docs/specs/ wins for architecture contract.
2. spec/generated/csr_map.json wins for CSR offsets and bit fields.
3. generated SV/C/Python headers win over hand-written consumer code.
4. platform/de1soc/address_map/hps_bridge_regions.json wins for the reviewed board-specific source freeze.
5. platform/de1soc/address_map/address_map.md is the human-readable rendering of that freeze.
6. platform/de1soc/address_map/sopcinfo_location.md defines the only accepted generated-evidence location.
7. sw/hps/config/trecap_hps_config.json wins for runtime execution on a specific board image but must pass parity with the frozen map.
8. Comments inside C/SV/Python files do not win over any of the above.
```

## What not to hard-code

Forbidden hard-coded implementation literals:

```text
- CSR base physical address inside HPS C source;
- DDR ring base inside RTL source;
- CSR offsets inside HPS C source outside generated headers;
- packet payload sizes inside Python parser outside generated constants;
- Linux userspace virtual pointer written to RING_BASE;
- direct DDR ring path inside rtl/telemetry/;
- platform-specific address constants inside rtl/core/.
```

Allowed local constants:

```text
- local derived offsets from generated constants;
- compile-time dummy values in a bring-up script clearly marked as example;
- board-specific values in runtime JSON and platform address-map docs;
- generated constants emitted by scripts/gen_headers.py.
```
