# PC dashboard bring-up

File class: **[1] hand-written bring-up document**.

This document defines the bring-up plan for the T-RECAP Phase 2 PC dashboard.

The PC dashboard is the last consumer in the live telemetry path:

```text
FPGA core taps
  -> telemetry packetizers
    -> DDR ring writer
      -> HPS DDR ring reader
        -> HPS UDP streamer
          -> PC dashboard
```

It also initiates the reverse command path:

```text
PC command client
  -> HPS command parser
    -> HPS command bridge / sequence-result cache
      -> generated CSR writes and readback
        -> FPGA safe-boundary/replay owners
```

The dashboard is an observability and control tool. It is not a bit-accurate signoff authority.

## Authority

The active integrated Phase 2 specification under `docs/specs/` is the authority. This file follows the Revision G dashboard contract:

```text
1. The parser consumes generated packet constants.
2. The GUI does not redraw on every UDP datagram.
3. UDP receive and packet parsing must not block plotting.
4. Sequence gaps are detected from normal forwarded telemetry records.
5. WRAP and diagnostic STATUS packets are excluded from sequence-gap detection.
6. dma_drop_count and packet_fifo_drop_count are displayed separately.
7. PC commands are accepted only through the HPS command server and safe CSR mechanisms.
```

## Step 15 source implementation status

Step 15 completes the checked-in dashboard source architecture:

```text
UDP receive/parser thread
  -> strict generated packet parser
  -> bounded telemetry/display buffers
  -> fixed-rate GUI snapshot
      -> dedicated x[n-D]/y[n] waveform
      -> dedicated time-domain error
      -> latest spectrum
      -> bounded SPEC64 or SPEC129 heatmap keyed by frame_idx
      -> locally toggleable mask/suppression overlay
      -> metrics and status/loss panels

live control event
  -> one persistent asynchronous serialized CommandClient
  -> HPS command server
  -> visible command result event
```

The source/host gate also covers packet-rate calculation, distinct loss domains,
malformed/truncated visibility, recorded-timestamp capture replay, and validated
capture append. It does not prove a live HPS/FPGA UDP stream, a ten-minute GUI
soak on the demo PC, an actual CSR mutation/result in hardware, or core signoff.

## Preconditions

Do not start full dashboard integration before these are true:

```text
[ ] Generated packet constants exist or the missing R1 generator is explicitly tracked.
[ ] HPS Ethernet M0 dummy UDP works.
[ ] HPS CSR M1 works.
[ ] DDR ring STATUS-only M2 works or a file-based packet capture is available.
[ ] Dashboard can import generated packet constants.
[ ] The active PC/HPS IP addresses and UDP ports are recorded.
```

A parser-only bring-up can begin earlier using captured packet binaries, but that does not prove the live transport path.

## Dashboard responsibilities

The dashboard shall support these panels:

```text
1. waveform: delayed input x[n-D] and reconstructed output y[n]
2. error: e[n] = x[n-D] - y[n]
3. spectrogram: SPEC64 or SPEC129
4. mask/suppression: overlay or bucket-level suppression ratio
5. metrics: eligible suppression ratio and kept-energy ratio
6. status: active THR2, source mode, packet enables, drop counters, overflow flags, packet rate, sequence gaps
7. live command controls: PING, SET_THR2, CLEAR_METRICS, SET_SOURCE_MODE,
   SET_PACKET_ENABLE/profile, SET_WAVE_DECIM, SET_SPEC_SHIFT, SET_SPEC_MODE,
   SET_TELEMETRY_ENABLE, CONFIGURE_DDR_RING, RESET_TRANSPORT, CLEAR_COUNTERS,
   START_BRAM_REPLAY, and READ_STATUS_VERSION
8. command result: queued/running/completed state plus disposition, reject reason,
   raw STATUS/VERSION, timeout, or local failure
```

The dashboard must display:

```text
dma_drop_count              # DDR-writer/ring-space/oversized/writer-policy drops
packet_fifo_drop_count      # pre-writer packet FIFO or telemetry tap drops
```

These counters must not be merged.

## Software architecture

Required internal separation:

```text
udp_receiver.py       -> nonblocking socket receive loop, background thread or async task
packet_parser.py      -> strict binary parser using generated constants
ring_buffers.py       -> bounded PC-side history buffers, no unbounded memory growth
plots.py              -> plotting primitives only
dashboard.py          -> GUI/window/application wiring
command_client.py     -> PC-to-HPS command packets
config.py             -> typed dashboard config loading
```

The running GUI owns one command worker and one `CommandClient` session. Button
callbacks enqueue typed commands; only that worker performs command socket I/O.
It serializes requests, preserves one monotonic version-2 sequence stream, and
publishes result events back to the dashboard. A GUI callback shall not create a
new default-sequence client, wait for UDP command I/O, or bypass HPS validation.

Loss and truncation state is separated by ownership:

| Display field | Owner and meaning |
| --- | --- |
| PC queue drops | Local dashboard event queue overflow. |
| PC parser errors | Datagram reached the parser but violated the wire contract. |
| PC truncated/oversized datagrams | Local socket receive/truncation or UDP-size observation. |
| `payload_truncated` | Wire flag on a valid telemetry payload; not a parser failure. |
| HPS malformed/oversized/send counters | HPS DDR validation or UDP forwarding state from STATUS. |
| `packet_fifo_drop_count` | FPGA pre-writer telemetry loss. |
| `dma_drop_count` | FPGA DDR-writer/ring-space loss after writer admission. |
| local sequence gaps | PC-observed normal forwarded sequence discontinuities. |
| HPS sequence gaps | HPS-owned STATUS counter; displayed separately from the local count. |

Forbidden behavior:

```text
[ ] packet parser duplicates hand-coded offsets instead of importing generated constants
[ ] GUI thread performs blocking socket receive
[ ] receive loop blocks on plot drawing
[ ] dashboard computes FFT/IFFT/mask/WOLA/reconstruction for the core
[ ] PC dashboard output is used as BRAM replay signoff
[ ] command client writes CSRs directly, bypassing HPS validation
```

### P4: WAVE plot

Goal: display delayed input, reconstructed output, and error.

WAVE payload semantics:

```text
sample_base = first represented output sample index
nsamp       = number of sample triples
channels    = 3
stride      = active WAVE_DECIM
sample[i]   = xdel, yout, err
```

Time axis rule:

```text
sample_index[i] = sample_base + i * stride
```

Do not plot WAVE as `sample_base + i` when stride is not 1.

Pass condition:

```text
[ ] The waveform view plots x[n-D] and y[n].
[ ] A dedicated error view plots e[n], independently of waveform visibility.
[ ] sample stride is respected.
[ ] buffer length is bounded.
[ ] receive thread does not block on drawing.
[ ] dashboard survives missing WAVE packets.
```

### P7: command client

Goal: prove PC-to-HPS command path without bypassing HPS validation.

Command packet requirements:

```text
magic   = 0x54524343
version = 1 exact Revision-G baseline, or 2 explicit Step-14 extension
length  = 28 bytes
crc32   = 0 in Revision G
```

Version 1 stays exactly seven commands with no generic result. Every version-2
non-PING command returns exactly 32 bytes with result magic `0x54524352`, echoed
command type and sequence, disposition, reject reason, raw STATUS, raw VERSION,
and zero CRC. PING in either version returns only a fresh diagnostic STATUS with
`seq=0` and has no RFC1982 ledger/cache effect.

All commands except PING and `READ_STATUS_VERSION` require CSR ID/VERSION 1.8
before `NOOP` or `APPLIED`. `READ_STATUS_VERSION` is the diagnostic exception:
it returns raw STATUS/VERSION as `NOOP` even for an incompatible FPGA image; only
a read failure returns `FAILED`.

Supported command smoke sequence:

```bash
python sw/pc_dashboard/scripts/run_dashboard.py \
  --config sw/pc_dashboard/configs/dashboard_direct_link.json \
  --command-protocol-version 1 \
  --ping

python sw/pc_dashboard/scripts/run_dashboard.py \
  --config sw/pc_dashboard/configs/dashboard_direct_link.json \
  --command-protocol-version 2 \
  --ping \
  --reset-transport \
  --configure-ddr-ring \
  --set-wave-decim 2 \
  --set-spec-mode 1 \
  --set-spec-shift 20 \
  --set-packet-profile status-only \
  --enable-telemetry \
  --read-status-version
```

The v2 lifecycle options must execute RESET, CONFIGURE, safe control mutations,
and ENABLE in that order even if CLI flags are written in a different order.
Use one bound client session so mutation sequences advance monotonically; do not
start separate default-sequence processes for each command.

The Step-15 live controls reuse the same command implementation. The dashboard
creates one persistent client session and routes every control action through one
asynchronous serialized worker. A command remains visible as queued, running,
then completed or failed. For a version-2 non-PING request, the completed display
includes the disposition, reject reason, raw STATUS, and raw VERSION. PING shows
its diagnostic STATUS response and never fabricates a generic command result.

`CONFIGURE_DDR_RING` is a button/action with all-zero wire arguments; there is no
dashboard field for a network-supplied physical DDR address. A packet/telemetry
profile maps to generated `SET_PACKET_ENABLE` and `SET_SPEC_MODE` commands instead
of inventing a new wire command.

Pass condition:

```text
[ ] PING returns a STATUS packet, not an undefined ACK packet.
[ ] Canonical command socket binds 192.168.10.1:5007 and targets 192.168.10.2:5006.
[ ] v1 still accepts exactly the original seven types and emits no generic result.
[ ] Every v2 non-PING result is exactly 32 bytes and validates echoed type/sequence.
[ ] An identical v2 retry receives the byte-identical cached result without reapplication.
[ ] Same sequence with different bytes conflicts; stale/ambiguous RFC1982 sequence rejects.
[ ] RESET_TRANSPORT -> CONFIGURE_DDR_RING -> SET_TELEMETRY_ENABLE 1 is enforced.
[ ] CONFIGURE_DDR_RING accepts only all-zero args and cannot carry a physical address.
[ ] Safe control mutations verify disabled/epoch-idle/replay-idle, readback, and restore.
[ ] SET_THR2 writes THR2_LO, THR2_HI, then THR2_COMMIT through HPS.
[ ] Active THR2 changes only at a frame boundary.
[ ] Out-of-range THR2 is rejected and counted.
[ ] Reserved packet-enable bits are rejected.
[ ] PEAKS_EN and DEBUG_EN remain rejected in the baseline.
[ ] Zero WAVE_DECIM is rejected.
[ ] Command source IP is checked.
[ ] Live controls use one persistent client and one serialized sequence stream.
[ ] Command I/O does not block telemetry receive or the GUI refresh loop.
[ ] Command disposition/reason/readback or local failure is visible.
```

### P8: sequence-gap and packet-loss behavior

Goal: make loss visible without crashing.

Sequence rule:

```text
expected_next = (previous_seq + 1) mod 2^32
```

Dashboard must exclude:

```text
WRAP records                                # not forwarded and no PC-visible seq
HPS diagnostic STATUS with status_diagnostic # seq ignored
pre-commit FPGA drops                        # visible via counters, not seq gaps
```

Test method:

```text
1. Capture a known packet stream.
2. Drop one normal packet in a test harness or replay file.
3. Confirm dashboard increments sequence_gap_count.
4. Inject a diagnostic STATUS; confirm no sequence gap is counted.
```

Pass condition:

```text
[ ] sequence gaps are displayed.
[ ] missing packets do not crash plots.
[ ] gap logic wraps correctly at 2^32 - 1 to 0.
[ ] drop counters and sequence gaps are explained separately.
```

Packet rate is computed from packet receive timestamps over a bounded recent
window. It is not derived from GUI redraw count, so changing the 20-30 Hz display
cadence does not redefine the measured transport rate. Capture replay supplies
the original recorded receive timestamps to the same calculation.

No loss counter is a substitute for another. In particular, a local PC queue
drop does not increment `packet_fifo_drop_count`; a local parser error does not
become an HPS malformed-DDR count; and a pre-commit FPGA drop is visible through
its owner counter rather than a fabricated PC sequence gap.

Goal: prove the dashboard does not become the bottleneck.

Recommended full first-demo packet profile:

```text
STATUS    = 5 to 10 Hz
METRICS   = 20 to 30 Hz
WAVE      = full-rate at 48 kS/s or decimate by 2
SPEC_MODE = SPEC64 first
```

Soak pass condition:

```text
[ ] receive thread stays alive.
[ ] GUI redraw rate stays near configured 20 to 30 Hz.
[ ] bounded buffers do not grow without limit.
[ ] CPU usage is acceptable on demo PC.
[ ] closing dashboard does not stall FPGA core.
[ ] reconnecting dashboard works after HPS keeps consuming DDR ring.
```

## Capture and replay

Every meaningful dashboard demo should be reproducible from a raw packet capture.

Save:

```text
artifacts/telemetry_captures/<capture_name>/packets.bin            [2]
artifacts/telemetry_captures/<capture_name>/capture_manifest.json  [2]
```

Manifest minimum:

```json
{
  "capture_name": "pc_dashboard_full_demo_status_wave_metrics_spec64",
  "source_mode": "bram_replay",
  "packet_enable": ["STATUS", "WAVE", "METRICS", "SPEC"],
  "spec_mode": "SPEC64",
  "wave_decim": 1,
  "telemetry_port": 5005,
  "command_port": 5006,
  "transport_version_major": 1,
  "transport_version_minor": 8,
  "dashboard_git_commit": "<fill-in>",
  "notes": "Capture used to reproduce dashboard plots. Not a core signoff artifact."
}
```

Every framed capture record stores its receive timestamp. Replay mode uses that
timestamp when it feeds the same parser and ring-buffer path as live UDP, which
keeps packet-rate and history tests deterministic. Do not maintain a second
parser for capture files.

When append is requested, the writer validates the existing `TRCPUDP1` stream,
seeks to its end, and appends complete framed records. It shall not overwrite the
capture or write another magic header. A malformed existing capture fails closed.

## Failure modes

| Symptom | Likely cause | First check |
| --- | --- | --- |
| no packets | firewall, wrong bind address, wrong HPS IP/port | `smoke_udp_recv.py` |
| parser rejects all packets | endian/magic compare or stale generated constants | `trecap_packet.py` and header hex dump |
| STATUS works but WAVE fails | WAVE payload size/stride parser bug | WAVE nsamp/channels/stride fields |
| GUI freezes | plotting on receive thread or redraw per datagram | separate receiver and GUI loops |
| sequence gaps increase during WRAP | WRAP forwarded or counted incorrectly | HPS reader and dashboard gap logic |
| kept-energy ratio shows 0 on silence | denominator-zero bug | display N/A when total is zero |
| command ignored | wrong PC source IP, HPS rejects, command port wrong | HPS command_server log |
| THR2 updates immediately mid-frame | FPGA CSR commit bug | THR2 pending/active STATUS fields |
| drop counters merged | STATUS parser/display bug | separate dashboard fields |
| dashboard says core failed | misuse of live telemetry as signoff | run BRAM replay signoff instead |

## Stop conditions

Stop dashboard bring-up and fix lower layer if:

```text
[ ] HPS forwards malformed records instead of disabling telemetry.
[ ] Parser accepts reserved flag bits silently.
[ ] Dashboard command client bypasses HPS validation.
[ ] GUI thread blocks socket receive.
[ ] Memory use grows unbounded during live streaming.
[ ] Dashboard computes the core algorithm in software and presents it as hardware output.
[ ] Dashboard is used as the only proof of correctness.
```

## Acceptance checklist

A Step-15 source package is checked with:

```bash
make dashboard-import
make dashboard-step14-test
make dashboard-step15-test
make step15-source
```

The Step-15 host gate covers strict synthetic STATUS/WAVE/METRICS/SPEC64/SPEC129
parsing, dedicated waveform/error display models, latest-spectrum and bounded
frame-indexed heatmap models, denominator-zero metrics, packet-rate calculation,
modulo sequence gaps, distinct loss/truncation domains, persistent serialized
command dispatch with visible results, and timestamp-preserving capture
replay/append. This is source/host evidence only.

Final live dashboard acceptance still requires all of the following unchecked
bring-up items:

```text
[ ] Real STATUS, WAVE, METRICS, and one spectrum mode arrive from the live HPS/FPGA UDP path.
[ ] STATUS-only live display works before other packet types are enabled.
[ ] Live WAVE respects sample_base/stride and the hardware error channel is visible.
[ ] The latest spectrum and bounded heatmap update from real frame_idx values.
[ ] dma_drop_count and packet_fifo_drop_count change only in their real ownership domains.
[ ] Live malformed, oversized, UDP-send, parser, and payload-truncated states are attributable.
[ ] The GUI sustains a measured 20-30 Hz update cadence during a ten-minute demo-PC soak.
[ ] Live controls bind the exact command peer and return real HPS/FPGA results.
[ ] PING returns a live diagnostic STATUS; no undefined ACK appears.
[ ] RESET -> CONFIGURE -> ENABLE and safe mutations produce verified hardware CSR results.
[ ] SET_THR2 follows HPS validation and the FPGA shadow/frame-boundary commit in hardware.
[ ] Invalid live commands are rejected and counted without modifying active hardware state.
[ ] Closing the dashboard does not stall FPGA core processing.
[ ] A real capture can be appended, replayed with original timestamps, and rendered through the same parser.
```

No live HPS/FPGA UDP exchange, ten-minute soak, hardware CSR result, or hardware
non-stall behavior is claimed until those items are recorded as external bring-up
evidence. Even after they pass, the dashboard remains demo observability and
control; it cannot replace BRAM replay plus golden-artifact correctness signoff.
