# Audio LINE-IN bring-up

File class: **[1] hand-written bring-up document**.

This document defines the bring-up plan for using DE1-SoC audio LINE-IN as a live input source for the Phase 2 T-RECAP core.

LINE-IN is a live demonstration source. It is not the bit-accurate correctness source. Correctness remains:

```text
reference artifacts
  -> BRAM replay source
    -> FPGA STFT/WOLA core
      -> artifact comparison
```

The LINE-IN path is:

```text
DE1-SoC audio connector
  -> audio codec wrapper
    -> trecap_audio_adapter.sv
      -> trecap_source_mux.sv
        -> trecap_source_core_integration.sv
          -> FPGA STFT/WOLA core
            -> valid-only telemetry taps
              -> telemetry / DDR / HPS UDP
                -> PC dashboard
```

Step 16 completes this path in checked-in source. The physical
`de1_soc_trecap_top.sv` instantiates a peripheral-only 12.288 MHz audio PLL,
FPGA-side open-drain WM8731 initialization, and the codec I2S wrapper. The codec
is configured at 7-bit address `0x1a` for 48 kS/s, signed 16-bit I2S with the
codec as BCLK/LRCK master. Complete stereo frames cross to `clk_fabric` through
an async FIFO before `trecap_source_core_integration.sv` applies the frozen
audio scaling, registered source selection, transition guard, core
discontinuity clear, and real tap boundary. A second async FIFO carries the
best-effort processed monitor stream back to codec BCLK.

LINE-IN operation on hardware remains unestablished. Native RTL source
compilation, actual Platform Designer generation, and native11 placement/routing
now exist. The implemented external timing policy is documented in
[physical_timing.md](../architecture/physical_timing.md); each source revision
still needs its corresponding fitted reports. Current build results and gates
are recorded in [architecture_implementation.md](../architecture/architecture_implementation.md)
and [build_order.md](../architecture/build_order.md). Standard Edition evaluation
mode has not produced a programmable SOF. Functional verification, measured PLL
frequency/lock, codec I2C ACKs, BCLK/LRCK, and live samples remain pending.
Artifact-driven BRAM replay remains the correctness prerequisite.


## Stage boundary

LINE-IN is R11 work. Do not start this file before:

```text
[ ] C0 has passed or the remaining C0 gap is documented.
[ ] BRAM replay has at least one known artifact-driven physical-board pass.
[ ] T0 transport has STATUS-only working.
[ ] DDR ring writer has passed basic STATUS/WAVE streaming.
[ ] PC dashboard parser can display STATUS and WAVE from BRAM replay or diagnostic source.
[ ] Step-7 source-mode contract/static checks pass; functional transition evidence remains pending.
[ ] Step-16 audio source contract/profile checks pass.
```

If LINE-IN is started before these, failures will be ambiguous. You will not know whether the bug is in the core, source adapter, DDR ring, HPS streamer, dashboard parser, or the physical audio source.

Step-16 source gates are:

```bash
make check-profiles
make check-de1soc-audio-path
make check-step16-audio-model
```

These checks validate the frozen source contract and a host-side behavioral
model only. They are not native RTL compilation/simulation, timing, I2C, or
hardware evidence.

## What LINE-IN must prove

A passed LINE-IN bring-up proves:

```text
[ ] The board audio codec wrapper produces a stable sample tick.
[ ] Audio samples are converted into signed N = 12 core scale by a frozen rule.
[ ] Source-mode switching into audio mode does not mix old-source state with new-source state.
[ ] The core continues processing live samples.
[ ] WAVE telemetry shows delayed input x[n-D], y[n], and error e[n].
[ ] Threshold changes still apply through THR2 shadow/commit.
[ ] The demo remains stable for a controlled live run.
```

It does not prove:

```text
[ ] artifact equality against reference outputs, because the input is live and not frozen
[ ] exact no-suppression zero error, because Phase 2 fixed-point STFT/WOLA is near-lossless, not Phase 1 exact identity
[ ] Quartus/TimeQuest closure, measured clock rates, I2C ACKs, or correct analog hardware merely because source checks pass
[ ] true board power reduction
[ ] that the audio codec itself is calibrated as a measurement instrument
```

## Physical setup

Start with conservative audio levels.

Recommended first physical connection:

```text
1. PC or phone headphone output -> DE1-SoC LINE-IN
2. Signal level low at first; increase only after no clipping is observed
3. Optional DE1-SoC LINE-OUT -> powered speaker or oscilloscope only after input path works
4. HPS UART connected for source-mode/debug logs
5. RJ45 connected if dashboard telemetry is used
```

Do not feed speaker-amplifier outputs into LINE-IN. Use line-level or headphone-level output only. Start muted, then increase slowly.

## Source contract

The core consumes signed samples:

```text
x[n] in signed N-bit two's-complement scale
baseline N = 12
range = [-2048, 2047]
```

For an audio-codec source whose sample width is `Baudio >= N`, the adapter rule is:

```text
x[n] = satN(rnd_shr(aaudio[n], Baudio - N))
```

This rule assumes `aaudio[n]` is a signed audio sample centered at zero. If the codec wrapper delivers unsigned samples or left-justified packed samples, `audio_codec_wrapper.sv` must first expose a documented signed sample before `trecap_audio_adapter.sv` applies the scale rule.

If `Baudio < N`, do not improvise. Freeze a left-shift or sign-extension rule in the profile and document it before implementation.

## Stereo policy

The first implementation uses a single mono channel.

Baseline policy:

```text
selected_audio_channel = left
right_channel_policy   = ignored for core input
lineout_policy         = optional processed mono duplicated to left/right, or disabled
```

Do not silently average left and right. If the team wants stereo averaging later, define the exact signed rounding rule and update `config/profiles/de1soc_linein_demo.json`.

## Codec-bus ownership and readiness

The DE1-SoC HPS/FPGA mux must grant the codec control bus to FPGA logic:

```text
HPS_I2C_CONTROL = 0
qualified audio PLL lock = 1
FPGA codec-bus grant = 1
    -> accept codec-init start
codec init done with no error = 1
    -> admit I2S capture and optional line-out
```

The FPGA never drives `HPS_I2C_CONTROL`. It only observes the synchronized grant
and fails closed if HPS selects itself. `FPGA_I2C_SCLK` is on `PIN_J12` and
`FPGA_I2C_SDAT` is on `PIN_K12`; both use 3.3-V LVTTL open-drain behavior and
depend on the board pull-ups. Do not enable an internal weak pull-up or replace
that electrical behavior with push-pull high drive.

The frozen control rate is 100 kHz. Every transmitted byte requires an ACK; a
register write may retry at most three times after its initial attempt. The
codec ACTIVE write is last, and configuration-done is legal only after all
writes are acknowledged.

Codec readiness gates audio admission, not fabric hard reset. Loss of readiness
mutes/flushes the monitor and stops new captured samples without resetting the
mathematical core or changing the canonical 50 MHz fabric reset policy.

## Source-mode commit rule

Switching into or out of audio source mode must not splice different sources into one continuous core interval.

Implemented source-level transition sequence:

```text
1. HPS writes SOURCE_MODE_SHADOW and SOURCE_MODE_COMMIT.
2. CSR logic waits for the real selected-source safe boundary and updates the complete active enum.
3. The post-safe-boundary apply pulse reaches trecap_source_core_integration.
4. A non-idempotent change immediately blocks source ready/valid acceptance.
5. Source adapter epoch state and source-dependent core rings/scheduler/alignment are cleared.
6. The registered mux selects audio and emits a discontinuity pulse.
7. The first audio beat remains held until the transition guard is released.
8. Telemetry observes subsequent real taps and cannot stall the source/core path.
```

A command that writes source mode directly into active core state is invalid.

## Bring-up ladder

### A0: codec wrapper compile and pin binding

Goal: obtain Quartus evidence that the already-connected platform wrapper builds before debugging audio data.

Checklist:

```text
[ ] `audio_codec_wrapper.sv` is listed in the full-board filelist and remains outside C0 top dependencies.
[ ] `audio_pll_wrapper.sv` and `audio_codec_i2c_init.sv` precede the codec wrapper and board top in dependency order.
[ ] Audio pins are assigned in `constraints/de1soc/pin_assignments.tcl` or QSF.
[ ] `FPGA_I2C_SCLK`/`FPGA_I2C_SDAT` are open-drain at the documented board pins; `HPS_I2C_CONTROL` is not an FPGA output.
[ ] Board clocks/resets are documented in `clock_reset_plan.md`.
[ ] CDC from audio bit clock/sample strobe into core clock is documented in `cdc_plan.md`.
[ ] `make quartus-de1soc` selects physical top `de1_soc_trecap_top` and includes the wrapper only in the full board image.
```

Pass condition:

```text
[ ] Quartus compiles physical top `de1_soc_trecap_top` with `audio_codec_wrapper` and `trecap_source_core_integration` instantiated.
[ ] The build contains exactly one audio PLL, one codec I2C initializer, and one codec wrapper.
[ ] Core-only build remains independent of audio wrapper.
```

### A1: codec configuration and sample tick

Goal: prove the codec produces stable samples before connecting the core.

Recommended debug signals:

```text
audio_sample_valid
audio_left
audio_right
audio_sample_count
audio_codec_init_done
audio_codec_init_error_sticky
audio_codec_nack_sticky
audio_pll_locked
audio_i2c_bus_grant
audio_rx_overflow_count
audio_tx_overflow_count
audio_tx_underflow_count
```

Pass condition:

```text
[ ] Codec configuration completes.
[ ] `HPS_I2C_CONTROL` remains low for the entire FPGA initialization transaction.
[ ] I2C writes receive ACKs and the ACTIVE register is written last.
[ ] Sample valid toggles at the configured rate, expected first target 48 kS/s.
[ ] `AUD_XCK`, `AUD_BCLK`, and LRCK measure 12.288 MHz, 3.072 MHz, and 48 kHz respectively for the frozen profile.
[ ] Sample counter increments monotonically.
[ ] Reset release is synchronized into the audio/platform domain.
[ ] RX overflow, TX overflow, and TX underflow counters remain zero for the nominal test.
```

If sample valid is unstable, do not debug the STFT core yet.

### A2: adapter scaling smoke

Goal: prove audio samples map to signed N-bit core scale without clipping under normal input volume.

Procedure:

```text
1. Feed a low-volume sine tone or quiet music into LINE-IN.
2. Keep THR2 at 0 or a low value.
3. Read debug min/max counters from adapter or display through STATUS if implemented.
4. Confirm values occupy a sensible signed 12-bit range.
```

Expected first-pass range:

```text
quiet input        -> values near zero
moderate sine      -> symmetric positive/negative swing
excess volume      -> clipping near -2048 or +2047; reduce volume
no cable connected -> small noise or near-zero, depending on board analog path
```

Adapter debug taps, if implemented separately from the frozen Step-16 transport
counters:

```text
audio_sample_count
audio_min_sample
audio_max_sample
audio_clip_count
audio_adapter_overflow
```

The implemented Step-16 counters are saturating 64-bit
`audio_rx_overflow_count`, `audio_tx_overflow_count`, and
`audio_tx_underflow_count`. Each saturates at all ones and clears with the
wrapper `clear_sticky_i` event. Keep them dedicated; do not map them onto
unrelated generated `OVERFLOW_FLAGS` meanings.

### A3: diagnostic source-to-audio source switch

Goal: prove source-mode commit behavior.

Procedure:

```text
1. Start in diagnostic source or BRAM replay source.
2. Confirm STATUS.source_mode reflects the old source.
3. Send `SET_SOURCE_MODE(audio_wrapper)` from PC or HPS console.
4. Observe source_commit_pending.
5. Confirm active source changes only at a safe sample/frame boundary.
6. Confirm metrics are cleared or discontinuity-marked.
```

Pass condition:

```text
[ ] No mixed-source WAVE segment is presented as continuous without discontinuity marking.
[ ] Core counters reset or continue according to the documented policy.
[ ] OLA/input-ring stale state is not carried into audio mode unless explicitly intended and documented.
[ ] `STATUS.source_mode` reports `audio_wrapper` after commit.
```

### A4: WAVE telemetry with audio input

Goal: see live audio as delayed input and reconstructed output on the PC dashboard.

Recommended packet profile:

```text
PACKET_ENABLE = STATUS_EN | WAVE_EN
WAVE_DECIM    = 1 or 2
SPEC_MODE     = 0 at first
METRICS_EN    = 0 at first
```

Pass condition:

```text
[ ] Dashboard shows x[n-D] moving with the audio source.
[ ] y[n] is present and time-aligned to x[n-D] according to WAVE sample_base/stride.
[ ] error plot remains bounded under no/low suppression.
[ ] STATUS reports no arithmetic/OLA overflow on normal-volume input.
[ ] UDP loss or dashboard slowdown does not stop core sample count.
```

### A5: threshold control on live audio

Goal: prove SET_THR2 still follows the frame-boundary commit rule under live input.

Procedure:

```text
1. Run audio source with STATUS + WAVE + METRICS.
2. Send SET_THR2 low value.
3. Confirm thr2_commit_pending then active THR2 update.
4. Send higher THR2.
5. Observe eligible_suppression_ratio trend and time-domain error trend.
```

Pass condition:

```text
[ ] THR2 changes through THR2_LO, THR2_HI, THR2_COMMIT.
[ ] Active threshold changes at a frame boundary.
[ ] Illegal THR2 values are rejected and counted.
[ ] HPS does not compute masking decisions.
```

### A6: add METRICS and one spectrum mode

Goal: show live spectral behavior without overloading the dashboard.

Recommended first full audio demo:

```text
sample_rate_hz = 48000
WAVE           = full-rate or decimate by 2
SPEC_MODE      = SPEC64 first if dashboard load is high
METRICS        = 20 to 30 Hz
STATUS         = 5 to 10 Hz
```

Pass condition:

```text
[ ] SPEC64 or SPEC129 plot updates without parser errors.
[ ] Suppression overlay or bucket ratio responds to THR2.
[ ] Both dma_drop_count and packet_fifo_drop_count are displayed separately.
[ ] Dashboard redraw rate is stable around 20 to 30 Hz.
[ ] Packet receive thread does not block on plotting.
```

### A7: optional line-out monitor

Goal: route processed output to audio LINE-OUT for human demo.

This is optional and must not be used as correctness evidence.

Checklist:

```text
[ ] Output scaling from N-bit y[n] to codec width is documented.
[ ] Saturation/clipping policy for line-out is documented.
[ ] Muting behavior on reset/source switch is implemented.
[ ] Source discontinuity flushes old FIFO epochs before a new monitor frame is emitted.
[ ] A primed TX FIFO miss emits digital silence and increments TX underflow without stalling the core.
[ ] No combinational path from audio input directly to output bypasses the core unless in an explicit debug mode.
```

If line-out causes noise, feedback, or clipping, disable it and continue with dashboard-only visualization.

```text

```

Recommended packet rates:

| Packet | First audio demo setting | Notes |

## Failure modes

| Symptom | Likely cause | First check |
| --- | --- | --- |
| no audio samples | PLL not locked, HPS owns codec I2C, codec init failed, wrong clock, reset stuck | PLL lock, bus grant, config done/error/NACK, sample counter |
| codec init never starts | `HPS_I2C_CONTROL` high or unsupported PLL/profile | mux ownership and supported-config status |
| codec init retries/aborts | I2C NACK, missing pull-up, bus ownership changed | ACK/retry/abort counters and open-drain pins |
| samples only positive or only negative | signed/unsigned conversion bug | codec wrapper sample interpretation |
| samples clip at rails | input volume too high or wrong shift | adapter min/max and clip counter |
| source switch creates huge transient | stale OLA/input ring or no discontinuity reset | source-mode commit sequence |
| dashboard freezes when audio starts | WAVE too high rate or GUI redraw per packet | dashboard receiver/GUI separation |
| spectrum looks mirrored/wrong bins | core issue, not audio wrapper first | BRAM replay and SPEC parser |
| THR2 change tears mid-frame | missing shadow/commit | CSR commit logic |
| drop counters rise immediately | dashboard/HPS bottleneck or packet schedule too aggressive | use STATUS-only then add WAVE |
| core sample count stops if dashboard closes | transport backpressure bug | non-stall path and FIFO/drop logic |
| line-out emits gaps after priming | monitor FIFO drained between codec frames | TX underflow counter; core remains non-stalling |

## Stop conditions

Stop LINE-IN testing if any of these occur:

```text
[ ] audio adapter outputs values outside signed N-bit range before saturation policy is applied
[ ] arithmetic_overflow or ola_overflow sets under low-volume input
[ ] source-mode switch corrupts core state without reset/discontinuity marking
[ ] core counters stop because PC/dashboard/HPS is slow
[ ] HPS or PC starts computing audio FFT/IFFT/mask/WOLA in software
[ ] line-out feedback or clipping risks speaker/headphone damage
```

## Acceptance checklist

A first LINE-IN demo is acceptable when:

```text
[ ] BRAM replay is still the documented correctness authority.
[ ] Audio wrapper compiles only in platform/full-board builds.
[ ] Explicit `de1soc_linein_demo` profile is selected; the default BRAM profile was not silently changed.
[ ] `AUD_XCK` measures 12.288 MHz and qualified lock remains stable.
[ ] WM8731 address `0x1a` initialization receives ACKs with `HPS_I2C_CONTROL=0` throughout.
[ ] BCLK/LRCK measure 3.072 MHz/48 kHz and 16-bit signed I2S framing is observed.
[ ] Audio adapter maps signed codec samples to N = 12 core samples using the frozen rule.
[ ] Source-mode change into `audio_wrapper` follows shadow/commit and safe reset/discontinuity behavior.
[ ] STATUS reports `source_mode = audio_wrapper` and live sample/frame counters.
[ ] WAVE shows x[n-D], y[n], and e[n] for live input.
[ ] THR2 command changes active threshold only through frame-boundary commit.
[ ] One spectrum mode and METRICS can run without crashing HPS or dashboard.
[ ] Drop counters remain separate and explainable.
[ ] Dedicated 64-bit RX-overflow, TX-overflow, and TX-underflow counters remain zero or each nonzero event is explained.
[ ] Ethernet disconnect or closed dashboard does not stall core processing.
```

Only after this checklist passes should LINE-IN be used for final demo recording.
