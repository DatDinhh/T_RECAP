# Reference model overview

This package implements the software reference for the T-RECAP Phase 2 selective-suppression core. The historical filename is retained for existing links. Source equations, generated outputs, imported snapshots, and final hardware evidence have distinct roles; running the software does not promote its output to final golden authority.

## Processing path

The model uses the following sequence:

1. Push normalized signed samples into the input ring.
2. Emit and clear the current OLA slot.
3. Every H samples, extract the most recent L samples with startup zero extension.
4. Apply the unsigned quantized square-root Hann analysis window.
5. Run the normalized radix-2 FFT and Hermitian canonicalization.
6. Compare canonical magnitude-squared values with THR2 and apply protection rules.
7. Apply the same mask to conjugate partners.
8. Run the unscaled IFFT, synthesis window, and OLA addition at offset G.

The batch runner continues through the full-tail geometry. The logical sample delay remains D = L + G. This model has no fabric-cycle, FIFO, or physical converter timing.

## Configuration and coefficients

The package's spec/generated/core_config.json supplies the source bindings generated by scripts/gen_config.py. The compiled model and Python tools consume those bindings instead of maintaining separate scalar copies.

Normal CLI execution reads five coefficient memh files from --coeff-dir. It checks their canonical input representation and declared hashes. The coefficient generation APIs remain available as explicit authoring tools; host floating-point coefficient generation is not part of the runtime path.

The CLI supports the pinned baseline. Public library calls also require matching configuration across run state, window, twiddles, and OLA ring. There is one threshold per run; frame-level functions accept a threshold when called explicitly.

## Ownership

The C++ source owns fixed-point arithmetic and output samples. Python owns convenient command-line orchestration and metadata handling. RTL, HPS software, dashboard behavior, source adapters, and board timing belong to their respective layers in the repository root.

The runtime writes a separate output configuration, preserves source configuration bytes, and adds reference run metadata. Inputs, coefficient files, generator provenance, and source manifests remain unchanged. See [runtime_contract.md](runtime_contract.md) for the exact behavior and [../README.md](../README.md) for build/run commands.

Imported artifacts and release-related utilities remain available for traceability and future project work. Their presence is not a claim that RTL verification or hardware acceptance has been completed.
